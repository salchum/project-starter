# T3 host adapter — supervised procedure

This is an agent-operated adapter specification, not an installed daemon or a
hard enforcement mechanism. Use live tool schemas; this document is not a frozen
API client. A host lacking these tools needs a separately validated adapter.

## Preflight and PM binding

1. Read orchestrator_capabilities. Validate the profile's provider, model, options,
   and child-task support. Check authentication through the approved subscription
   route; any failure blocks the affected work. Never configure API billing as fallback.
2. Read t3_project_list and match the project registry chosen during setup by Git remote identity. Resolve
   paths/project IDs at runtime; keep machine-specific IDs out of portable profiles.
3. Inspect t3_thread_list and recorded handoffs for existing PMs. Select one active
   accountable PM per repo; reconcile existing planning threads before replacing one.
4. When the user authorizes a new PM thread, use t3_thread_launch with explicit
   projectId, modelSelection, workspaceStrategy, and the bootstrap message.
   Use an existing isolated worktree or a new worktree for writing assignments.
   Put the message in message, not prompt. Inspect the returned binding/options.
5. Retain threadId. A lost launch response requires inspecting thread inventory
   before retrying: top-level launch has no idempotency key.

## Delegate and report

1. Verify all task prerequisites and slot reservation. Only the coordinator writes
   the global ledger; other PMs send requests and wait for the recorded reservation.
2. Bind the parent thread's workspace to the intended committed baseline and
   verify its full HEAD SHA matches the task packet before dispatch. Worktree
   delegation captures the parent's local commit and excludes uncommitted edits.
3. Call delegate_task with role, complete task packet, explicit target
   {providerInstanceId, model, options}, stable clientRequestId for that attempt,
   and mode async. For writers use isolation worktree.
4. Record the returned task ID and verify its model, options, and worktree. Require
   the child's preflight to verify its initial HEAD against the packet's base SHA
   before editing; a mismatch blocks implementation and is reported to the parent.
5. Wait for completion notification. Use task_status when reconciliation is needed.
   Account for hasPendingChildRuns and waiting_for_children: descendants must finish
   before releasing the parent assignment's obligations.
6. Persist the result and review the named revision. Each review round uses a new
   delegate_task with a distinct round request ID and full prior finding context.

## Thread settlement

After [the closure checks](../lifecycle.md) pass, the assigning manager calls
`t3_thread_organize` with `action: "settle"` and the exact temporary threadId.
Read back the thread and verify `settled: true`; record any failure instead of
claiming cleanup completed. Read task_status from the owning parent when needed
to detect pending descendant work, and thread state for active runs/requests.

Close eligible child threads before their parent. For a completed temporary
coordinator with no supervising agent, the human or coordinating conversation
performs closure. Do not settle an ongoing PM simply because its latest run ended.
If settling the current thread, T3 may defer settlement until the turn ends;
report that pending state accurately and verify it from the owner afterward.

## Cross-repository work

Top-level PM threads exchange explicit handoff messages using t3_thread_send and
acknowledge receipt with task IDs. They are not automatically children of the
coordination PM. Reconcile their status explicitly. Children belong to their repository
PM; changing shell directory does not change T3 project ownership.

## Pause, cancellation, recovery

A user disconnect leaves authorized work running within its limits. A pause
stops new dispatch; request a checkpoint from affected roles. For immediate stop,
task_cancel interrupts a delegated task and descendants. It is not transactional:
inspect partial files, processes, worktrees, and Git state before resuming.

A coordinated pause must reach every top-level PM and its descendants; cancelling
one child tree does not stop other PM threads. For a scope change, invalidate only
affected packets and approvals, then issue revised packets.

On restart: read durable thread/task state, inspect live processes and retained
worktrees, reconcile recorded attempts, and obtain a new explicit owner for any
abandoned assignment. Unknown liveness means blocked pending inspection, not a
free slot or a reason to duplicate execution.

## Limits and proof

Use the project's approved concurrency, correction, billing, and checkpoint limits
from ../operating-plan.md. Track reviewer/PM activity too. Initially run one leader
and one worker sequentially; this does not establish a global hard limit.

Tool wait timeout limits waiting, not execution. maxBatchThreads is not a global
concurrency cap. Prompt instructions and a Markdown ledger are cooperative policy,
not independent enforcement. No hard spend/deadline/uniqueness/recovery guarantees
are established by this foundation. Keep supervision until tests in ../rollout.md
pass and any required enforcing controls are separately implemented.
